Summary

Jordan was unable to run git status or git log in the Akira Website project directory. Git returned a fatal error indicating the directory was not a Git repository. Investigation revealed that the .git/HEAD file was empty (corrupted), and that underlying filesystem operations were timing out with mmap errors — indicating the repository was stored on an unstable or disconnected storage volume.

Root Cause

Two compounding issues were identified:

  • Corrupted .git/HEAD file: The HEAD file was empty (0 bytes of valid content), causing Git to reject the directory as a valid repository. This may have been caused by an interrupted write during a previous Git operation (e.g., a fetch or checkout that was killed mid-operation).

  • Filesystem/volume instability: Git's mmap system calls were timing out, which caused bus errors (SIGBUS / signal 10) on any operation that required reading pack files or object data from disk. This indicates the repository resides on an external drive, NAS, or network-mounted volume that became unresponsive.

Impact

  • Developer (Jordan) was fully blocked from all Git operations on the Akira Website repo.

  • No code was lost — working tree was clean and all commits were backed up on the remote.

  • No other developers or systems were reported as affected.

Resolution

Since git status confirmed the working tree was clean (no uncommitted changes), the safest and fastest resolution is to re-clone the repository from the remote:

cd ..

git clone <remote-url> Website-fresh

Any local config files (e.g. .env) should be copied across before swapping the folder. The corrupted folder can then be archived or deleted.

Lessons Learned

  • Storing Git repositories on external or network-attached volumes carries a risk of filesystem errors that can corrupt Git internals. Where possible, keep active repos on a local, reliable drive.

  • A bus error (signal 10) or mmap timeout during Git operations is almost always a storage problem, not a Git problem — skip Git debugging and go straight to disk diagnostics.

  • Keeping a clean working tree and pushing frequently means re-cloning is always a safe, zero-loss recovery option.
