Summary

Google Sign-In on the Android development build was completely non-functional. Tapping the “Sign in with Google” button opened the Google OAuth consent screen, which immediately displayed an “Access Blocked: Authorization Error” page with the message: “Custom scheme URIs are not allowed for WEB client types.”

Investigation revealed that the app was using expo-auth-session’s Google provider with the useProxy: true option, which historically routed OAuth redirects through Expo’s auth.expo.io proxy (an HTTPS endpoint that web OAuth clients accept). However, this proxy was deprecated and shut down in Expo SDK 49+. On SDK 54, the proxy flag is silently ignored and the redirect falls back to the app’s custom scheme (com.mugenyi.mvp://), which Google’s web-type OAuth client correctly rejects per OAuth 2.0 security policy.

The fix was to replace expo-auth-session’s web-based Google flow with the native @react-native-google-signin/google-signin library, which performs the entire OAuth exchange natively on-device without any redirect URIs.

Root Cause

Two compounding issues were identified:

  • Deprecated Expo auth proxy: The app relied on expo-auth-session’s useProxy: true option, which routed OAuth through https://auth.expo.io/@myndmap/MyndMap . This proxy was deprecated in Expo SDK 49 and fully removed by SDK 54. The flag is now silently ignored, causing the redirect URI to fall back to the app’s custom scheme (com.mugenyi.mvp://).

  • OAuth 2.0 security restriction: Google’s OAuth 2.0 implementation for “Web application” client types requires HTTPS redirect URIs. Custom scheme URIs (e.g. com.mugenyi.mvp://) are only permitted for “iOS” or “Android” client types. Since expo-auth-session uses the web client ID for its browser-based flow, the custom scheme redirect was correctly rejected by Google.

Impact

  • Google Sign-In was completely non-functional on Android. Users could not create accounts or sign in via Google.

  • Apple Sign-In (iOS) and Email Sign-Up/Login were unaffected and continued to work normally.

  • No user data was lost or compromised. The issue was isolated to the authentication entry point.

  • The app had not yet launched publicly on Android, so no end-users were impacted.

Resolution

The expo-auth-session Google provider was fully replaced with the native @react-native-google-signin/google-signin library. This library performs Google Sign-In entirely on-device using platform-native APIs, eliminating the need for web redirect URIs entirely.

Changes made:

  • MainOptions.js: Removed all expo-auth-session imports (Google, makeRedirectUri, useIdTokenAuthRequest). Added @react-native-google-signin/google-signin with GoogleSignin.configure() at module level. Rewrote handleGoogleSignIn to call GoogleSignin.signIn() natively, extract the ID token, and pass it to loginWithGoogle() in AuthContext.

  • app.json: Added the @react-native-google-signin/google-signin Expo config plugin with the iosUrlScheme set to the reversed iOS client ID.

  • AuthContext.js: No changes required. The loginWithGoogle(idToken) method continues to work identically — it receives an ID token and exchanges it via GoogleAuthProvider.credential() + signInWithCredential().

  • Native rebuild: Ran npx expo prebuild --clean followed by eas build --platform android --profile development to compile the new native module into the dev client.

Lessons Learned

  • Expo SDK major upgrades can silently deprecate core features. The auth.expo.io proxy removal was documented in Expo’s changelog but produced no runtime warnings — useProxy: true simply became a no-op. Always review breaking changes when upgrading SDK versions.

  • For production mobile apps, native authentication libraries (@react-native-google-signin) are more reliable than browser-based OAuth flows (expo-auth-session). Native libraries don’t depend on redirect URIs, proxy servers, or browser handoffs, and they provide a better user experience.

  • The error message “Custom scheme URIs are not allowed for WEB client types” is a Google-side OAuth security restriction, not a Firebase or Expo bug. Understanding OAuth 2.0 client type requirements (web vs. iOS vs. Android) would have shortened diagnosis time.

  • Native modules require a full rebuild (prebuild + eas build). Metro hot-reload cannot pick up new native code. This is expected behaviour for any library that ships with iOS/Android native source.
