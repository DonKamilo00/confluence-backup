Purpose of This Document

This page defines how MyndMap operates day-to-day — not just how code is written, but how decisions are made, how stability is protected, and how momentum is sustained as the product scales across iOS and Android.

It exists to:

  • Create clarity over chaos

  • Reduce operational risk during releases

  • Make future collaboration seamless

  • Protect long-term velocity and founder focus

Operating Philosophy

MyndMap is operated with the following principles:

1. Human-First, System-Driven

Decisions prioritize:

  • User mental load

  • Cognitive clarity

  • Predictable behavior over novelty

Systems exist to support humans, not the other way around.

2. Stability Before Speed

Shipping fast is meaningless if trust is lost.

We prefer:

  • Fewer releases

  • Higher confidence

  • Clean rollbacks when needed

3. Single Source of Truth

  • Confluence = how things are done

  • Git = what is shipped

  • App Stores = what users see

If it’s not documented, it’s not operationally real.

4. Platform Parity, Platform Respect

iOS and Android are:

  • Functionally aligned

  • Operationally separate

  • Released independently if needed

No platform blocks the other.

Operational Scope

Operations at MyndMap include:

  • Development workflow enforcement

  • Release coordination (iOS & Android)

  • Incident response

  • QA & testing standards

  • Post-release monitoring

  • Feedback intake & prioritization

Day-to-Day Operations

Daily Operations

Focus: Stability & awareness

  • Review crash logs (iOS / Android)

  • Monitor user feedback

  • Check API health & costs

  • Light UI/UX polish if required

No feature development should introduce instability into the current live build.

Weekly Operations

Focus: Direction & quality

  • Review in-progress features

  • Assess release readiness

  • Validate roadmap assumptions

  • Review platform-specific issues

Monthly Operations

Focus: Scale & reflection

  • Major feature or version release (if planned)

  • Metrics review (retention, sessions/device)

  • Cost vs value evaluation

  • Operational refinements

Decision-Making Framework

Decisions are evaluated using the following filters:

  1. Does this reduce user cognitive load?

  2. Does this improve long-term clarity?

  3. Does this increase operational risk?

  4. Can this be reversed safely?

If a decision fails any of the above, it is paused.

Incident Handling

Severity Levels

Level

Description

P0

App unusable / crash on launch

P1

Core feature broken

P2

UX or non-blocking issue

Incident Response Flow

  1. Identify platform (iOS / Android)

  2. Assess severity

  3. Pause new releases if needed

  4. Hotfix or rollback

  5. Document incident in Confluence

No incident is considered resolved until it is documented.

Release Ownership

  • Each release has one owner

  • That owner is responsible for:

    • Build integrity

    • Store metadata accuracy

    • Monitoring post-release health

For now, this role is held by Jordan Mugenyi.

Documentation Rules

  • All operational changes must be documented

  • Screenshots > assumptions

  • Checklists > memory

  • Clarity > brevity

What This Enables

By operating this way, MyndMap gains:

  • Calm releases

  • Faster recovery from issues

  • Easier onboarding of future contributors

  • Higher trust from users and partners

  • Founder mental clarity during scale
